## 风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 平台 DOM 或内部数据格式变化 | 扫描结果为空或不完整 | 多信号回退、脱敏 fixture、平台级回归测试 |
| 签名 URL 过期 | 预览可见但下载失败 | 缩短扫描到下载的间隔，明确提示重新扫描 |
| 分段视频流 | 下载到不完整文件 | 识别并拒绝分片 URL，只接受可验证的完整媒体源 |
| Service Worker 被回收 | 下载进度丢失 | 先持久化队列，并在启动时核对 Chrome 下载状态 |
| 过宽权限影响审核与信任 | 商店审核失败或用户拒绝安装 | 发布前执行权限审计，说明每项权限用途 |
| 平台条款或内容权利问题 | 合规风险 | 只处理当前账号可访问内容，不实现权限绕过，并提供清晰使用说明 |

## 发布流程

1. 更新 `extension/manifest.json` 的版本号。
2. 运行本地质量检查和六平台回归测试，记录实际完成范围。
3. 若发布 GitHub Release，创建与 Manifest 一致的标签，例如 `v1.0.2`。
4. 推送标签，触发 `.github/workflows/release.yml`；商店上传也可使用经过检查的本地构建包。
5. 验证上传 ZIP 的内容和 SHA-256 校验文件，不上传仓库根目录中遗留的旧 ZIP。
6. 从发布 ZIP 解压并完成一次干净安装验收。
7. 上传原有商店条目，保存并刷新核对说明；提交审核时确认“审核通过后自动发布”已勾选。
8. 记录送审版本和控制台结果；审核通过、自动发布完成后再更新上架状态。

GitHub Release、商店上传和审核状态分别记录，不能用其中一个替代另一个。1.0.2 本次未创建 Git 标签或 GitHub Release。
